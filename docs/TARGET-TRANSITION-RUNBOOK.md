## Manual recovery after ambiguous rotating WordPress refresh — current candidate

**Use only when Target details show a blocked refresh intent.** The Gateway deliberately will not use, disconnect, reauthorize or silently discard a credential while the remote issuer might have rotated it without delivering the successor. A definitive remote rejection can also preserve a blocked intent. Neither logout from the WordPress dashboard nor revoking the known old refresh token certifies revocation of an unknown successor.

1. **Stop and identify:** An authorized Gateway Owner with `security.manage` and `targets.disconnect` opens the exact Target details page. Record the immutable Target slug, the displayed WordPress origin and Gateway OAuth client metadata URL; never paste token material into a ticket, chat or log.
2. **Explicit blast-radius decision:** In the **same WordPress origin**, an authorized WordPress administrator opens **WP AI Bridge → OAuth Clients**, removes the exact Gateway metadata URL from **Approved OAuth Clients**, and **saves**. Under the pinned WordPress Bridge OAuth contract, **any** change to this additional-client list increments the shared revision and invalidates *every* existing non-ChatGPT additional-client authorization on that WordPress instance, not merely the selected Gateway Target. Any other affected integration must reauthorize. ChatGPT's built-in WordPress profile is not dependent on the additional-client revision. **Do not attempt this change if the collateral revocations are unapproved.** Gateway does not mutate WordPress approval settings remotely.
3. **Verify on WordPress:** Reload the OAuth Clients settings and verify the Gateway URL is absent in saved state; record an operator-controlled, non-secret change record. If access, verification or change approval is missing, **leave the Target blocked**. The Gateway intentionally does not claim to retrieve independent proof of this remote event.
4. **Settle and acknowledge:** Wait past any in-flight exchange and the Bridge's 60-second bounded recovery window. The Gateway enforces a minimum `max(75s, 60s + configured Bridge HTTP timeout + 15s)` from intent creation, but time alone is **not** revocation evidence. In the Target's Owner-only recovery form, check both attestations (confirmed saved remote change and impact on all additional clients), enter the exact Target slug and the Owner's current Gateway password. The hidden exact refresh intent ID fences stale browser tabs or an already completed rotation.
5. **Local single-Target cleanup:** The request atomically checks the credential ID, immutable Target, token generation, same pending intent and absence of conflicting revocation/callback work under a DB row lock. Only then does it delete that Target's encrypted local credential+metadata+refresh intent and mark its connection `disconnected` with `manual_revocation_attested`. A **required** Target-scoped Activity event `wordpress-refresh-remote-revocation-attested` (outcome `operator-attested`) is written in the **same transaction**; failed audit rolls back the cleanup. It does not contact WordPress, prove remotely revoked tokens, or modify other Gateway Targets and client-facing ChatGPT grants. A stale intent or operation conflict fails closed.
6. **Reauthorize safely:** After local cleanup, the WordPress administrator may restore the exact Gateway URL to the approved client list (another list revision change) and the Gateway Owner begins a **new** WordPress OAuth consent. Verify new connection/read/execute and disconnected old grants before allowing normal operation. Do not recover the old ciphertext or try unknown successor tokens. Preserve the WordPress-side revocation record for incident evidence.

**Evidence boundary:** The PHP feature tests simulate external operator attestation and verify local role, password, exact intent, lifetime, audit atomicity and Target isolation. An isolated MariaDB 11.8 multi-process test holds a refresh in network I/O while *separate processes* attempt refresh and disconnect; both fail closed, then the new generation is committed and revoked before disconnect. Neither test is actual WordPress remote proof. MariaDB 10.11 exact-candidate GitHub CI, real authorized non-production WordPress flow, ChatGPT reconnection and independent HIGH_ASSURANCE review are still required.

## Why this must be an explicit operator-visible upgrade

Site-era tables combine registered WP AI Bridge Targets, OAuth credentials, local user Target assignments, groups and check operations. A clean `Target` foundation is a breaking replacement. The owner explicitly accepts a **clean WP AI Bridge and ChatGPT/Gateway OAuth reconnect** after the next upgrade. Legacy Target-owned records and previously issued Gateway OAuth grants, access/refresh tokens, pending authorization codes and dependent refresh recoveries can all be invalidated. **Do not reset** administrator accounts, Gateway client signing/encryption keys, global permission denies, unrelated product data, or server data outside this Gateway.

The existing browser-updater recovery archive protects application **files/code**. It is **not a consistent database backup** and is never proof of database recovery after this migration. Migration DDL in MariaDB/MySQL is not transactionally reversible.

Before the final major upgrade is released, the operator must put the application in maintenance mode, create a **consistent, restorable database backup** outside the application/code backup, and ensure the rollback procedure is understood. Database backup and restoration must be tested in a non-production environment. Explicit values in the migration configuration confirm that the operator performed those steps; they are attestations, not an automatic backup.

Only known one-to-one denial strings are mapped (Gateway connection, `sites.*`/common Target rights, former `connections.*` and WP `abilities.*`). ## Deliberate confirmation gate — only after full integration and review

When any legacy Target-owned rows, Target-scoped Activity **or existing Gateway OAuth authorizations** exist, the migration requires both config-backed environment values:

```dotenv
GATEWAY_TARGET_RESET_ACKNOWLEDGED=RESET_TARGET_STATE
GATEWAY_TARGET_RESET_DATABASE_BACKUP_VERIFIED=RESTORABLE_DATABASE_BACKUP_VERIFIED
```

Do **not** configure these in a running production Gateway now. They are only valid for the explicitly approved, operator-prepared major upgrade. They are not passwords or recovery material and do not create or verify the backup.

If confirmation is missing or the old schema/denials/roles do not match the supported transition, the migration fails **before destructive DDL**. Once DDL begins, failures may leave an **unknown partial schema**; do not retry blindly, do not run `migrate:rollback`, do not reinstall over the existing database. Stop the updater and recover through the operator's independently verified database backup. Migration `down()` deliberately refuses to suggest a reversible restoration.
